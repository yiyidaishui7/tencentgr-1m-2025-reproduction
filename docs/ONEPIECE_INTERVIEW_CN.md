# OnePiece 复现：面试深挖问答

## 范围与可信度

### 1. 你复现的是完整 OnePiece 吗？

不是照搬所有模块。我复现的是最适合形成可验证主线的核心组合：OnePiece 的特征
编码、HSTU 序列编码器和带 LogQ 校正的 in-batch InfoNCE，并在同一离线协议下增加
Transformer 架构对照。SID、MoE、时间上下文、多模态门控和上游自定义多卡框架没有
混进第一轮正式实验，否则很难判断收益来自哪里。这叫资源缩放的核心方法复现，而不是
宣称完整重现上游最终榜单方案。

### 2. 为什么上游 0.1257/0.1319/0.1371 不能和你的分数直接比较？

上游技术报告中的数字对应其比赛后配置和评测链路，例如 8×512、24×512、12×1024；
我的数字来自固定 seed 的本地最后点击留出。两者模型规模、特征组合和评测协议都不完全
相同，因此只能把上游数字当方案背景，不能计算“复现率”或声称达到其榜单水平。

### 3. 为什么还要保留官方 Baseline 结果？

Baseline 是同一套 78,921 用户和 66 万候选离线协议上的参照系。它能回答“新方法在我
实际实现的协议下是否比已验证系统更好”；Transformer 对照则回答“差异是否来自 HSTU
编码器”。前者是系统级参照，后者是架构单变量对照，作用不同。

### 4. 如何证明没有目标泄漏？

验证用户的 Target 是最后一个 `action_type=1` Item，Query 只保留 Target 之前的事件。
我不仅在构造器里截断，还将 78,921 行用户、Target 和 prefix length 冻结为 NPZ，回查
原始 1M 序列，逐行确认 Target 正好位于 prefix、类型为点击且后面没有其他点击。协议
文件和行数组都有 SHA-256。

## 模型与目标函数

### 5. HSTU 和标准 Transformer 在代码里到底差在哪里？

两者都使用因果 Mask 和 Pre-LN。Transformer 是多头注意力加 Point-wise FFN，并使用
绝对位置 Embedding；HSTU 用一个统一块替代 MHA+FFN：先由单个线性层得到 U/Q/K/V，
用 SiLU 激活后的 QK 分数、可学习相对位置偏置和 V 做聚合，再用 U 做逐元素门控并经
输出投影。HSTU 不再使用单独的绝对位置表。

### 6. 为什么 HSTU 用 SiLU 权重而不是 Softmax？

这使注意力不再被约束为每行概率和为 1，并与 U 门控结合成数据依赖的选择与变换。
它也意味着输出尺度、Mask 和归一化更敏感，所以实验保留 Pre-LN、Dropout、梯度裁剪
与 BF16 稳定性检查。

### 7. InfoNCE 的正负样本如何构造？

每个有效序列位置的下一 Item 是正样本；同一 Batch 内其他有效位置的正 Item 同时作为
候选负样本。对归一化 Query/Item 向量计算温度缩放相似度矩阵，对角线是标签，再做
Cross Entropy。这比每个位置只采一个随机负样本提供了更强的排序信号。

### 8. 为什么要减去 `log q(item)`？

热门 Item 更容易出现在 Batch 中并成为负样本；不校正会对热门 Item 施加过强惩罚。
训练集交互频率给出采样概率 q，logit 使用 `similarity / temperature - log q`，近似校正
候选被采到的非均匀概率。我的实现只用训练用户统计 q，避免从验证目标获取分布信息。

### 9. 为什么 4×128 仍有约 4.92 亿参数？

参数主要不在四个序列块，而在 478 万 Item 的 32 维 ID 表、两个大质数哈希表，以及
多组稀疏特征 Embedding。缩小 HSTU 层数和 hidden 能减少计算与部分参数，但大词表仍
占主导。因此 HSTU 和 Transformer 控制组的总参数量分别为 491,793,216 和
492,013,584，仅相差 0.045%；效果比较主要反映编码器归纳偏置，而不是参数量大幅变化。

### 10. 14.9 万冷启动候选怎么处理？

660,000 候选中有 148,971 个不在训练 Item 索引。它们的 ID Embedding 回退到 padding
索引，但仍使用候选表提供的稀疏特征生成 Item 向量。这保留了“新 Item 依赖侧信息”的
能力。最终会把 cold-start 数量写进 metrics audit，不能假装所有候选都有训练 ID。

## 实验设计与资源

### 11. 为什么用 GPU4 和 GPU5 各跑一条，而不是两卡训练一个模型？

目标是完成架构对照，两个实验本身独立。各占一张 H200 能并行获得两组结果，且避免
DDP/自定义参数服务器带来的通信、全局 Batch 和负样本集合变化。这样每条仍是单卡
Batch 32，比较条件更清晰，也更适合共享机器上的故障隔离与断点恢复。

### 12. 你如何保证它是单变量对照？

两组固定同一个协议哈希、上游提交、特征输入、hidden=128、4 Blocks、4 Heads、
maxlen=101、Batch=32、6 Epoch、AdamW、warmup+cosine、BF16、InfoNCE 温度、训练 seed
和 66 万候选精确评测。脚本只用 `use_hstu` 选择 HSTU 或 Transformer，并把两组状态、
日志、checkpoint 和输出目录完全分开。

### 13. 为什么训练 loss 不能直接判断谁推荐得好？

InfoNCE loss 衡量当前 in-batch 候选上的分类难度，真实评测是在固定 66 万候选上看
Top-10；两者候选分布与尺度不同。模型选择必须看无泄漏检索指标，loss 只用于判断
收敛、数值稳定与训练异常。

### 14. 精确 66 万候选检索如何不爆显存？

候选向量以 8,192 一批编码并拼成 `660k × 128` 表；Query 以 128 一批计算
`128 × 660k` 分数，立即取 Top-10，不会物化完整 `78,921 × 660k` 矩阵。代价是计算
量仍高，但它消除了 ANN 近似误差，适合作为架构消融的正确性基线。

### 15. 为什么只跑一个 seed？

完整 1M 词表模型和精确评测在共享资源上成本较高，第一阶段先用一个冻结 seed 建立
可信点估计和工程闭环。逐用户配对区间只覆盖固定模型在评测人口上的差异，不包含训练
随机性；因此简历只能写“固定 seed 点估计”，不能写成稳定显著提升。后续最高优先级是
用多个 seed 复核赢家。

## 工程与交付

### 16. 上游代码遇到了什么问题？

两个直接阻塞是导入模块时动态执行 `pip install`，以及两个评分调用漏传
`interest_k`。前者破坏离线可复现环境，后者会在特定路径触发参数错误。我固定环境、
删除导入期安装并补齐参数，再通过合成、真实 Batch、小样本端到端和 1M 词表校准逐级
放大验证范围。

### 17. 为什么要做 100-step 校准再正式训练？

小样本通过只能说明逻辑通，不能证明 478 万 Item 词表在显存和吞吐上可行。校准实测
约 4.92 亿参数、峰值约 9.45 GiB，100 step 的 loss 从 17.07 降到 7.34，吞吐约
981 users/s，证明 H200 单卡有足够余量后才启动 6 Epoch 正式实验。

### 18. 共享机器上如何处理隐私与资源公平？

只使用用户授权的 GPU4/5，不检查其他用户任务内容、不抢占；所有远端目录逐层 700、
文件 600，进程名和路径保持中性。两个实验各自有原子状态、原子 checkpoint 和独立
清理边界，任何一路完成都只能清理自己的输出。

### 19. 产物为什么同时放 Hugging Face 和 GitHub？

GitHub 适合公开代码、协议说明、聚合指标、简历和面试文档，不适合多 GB 权重或受限
数据。Hugging Face Pro 私有仓库存模型、预测、完整日志、协议和 SHA 清单。每次都是
先在 D 盘验证，再上传并回读核验；Token 只走本机凭据，不出现在命令和日志。

### 20. 最终怎么判断项目完成？

两组训练和 78,921×660k 精确评测均完成；模型、指标、预测、配置、曲线和日志下载后
逐文件 SHA-256 通过；用户/Target/prefix 三组数组逐行一致；远端临时输出清理；HF
私有仓库文件完整；GitHub 公共分支包含可运行审计脚本、最终结果、简历表述和面试问答。
只有这些门槛全部满足，持续 goal 才标记完成。

### 21. 最终结果是什么，能得出什么结论？

HSTU 的 HR@10、NDCG@10、综合分为 0.0977433、0.0522325、0.0663408；同配置
Transformer 为 0.0939167、0.0501666、0.0637291。HSTU 综合分绝对提高 0.0026117，
相对提高 4.10%，固定评测人口的逐用户 95% 区间不跨 0。这个结论只适用于当前 seed
和 4×128 配置，不包含训练随机性。

### 22. 为什么分桶结果比总分更值得讲？

HSTU 在 0–20、21–50、51–80 历史桶的综合分相对 Transformer 分别提高 58.65%、
33.53%、7.07%，但在占 63.47% 用户的 81+ 桶低 0.93%。它说明总分 +4.10% 不是
“所有人群都更好”，而是短中历史收益与长历史轻微退化的加权结果。面试中我会把它
解释为一个待多 seed、位置偏置和更大容量实验验证的机制假设，而不是事后下因果结论。

### 23. 为什么不能说比 Baseline 提升 197% 就证明 HSTU 好？

HSTU 相对最佳 no-MM50 baseline 的系统级综合分点估计确实提高 197.19%，但两者同时
改变了容量、词表/侧特征参数化、BCE 对比 InfoNCE、Batch 和 Epoch。只有 HSTU 对
同配置 Transformer 的 +4.10% 是单变量架构证据；197.19% 只能作为端到端系统结果。
