# 面试展示讲稿

本讲稿对应 [3 页面试展示稿](INTERVIEW_DECK_CN.md)。三页全部是内容页，不单独占用封面。正常语速约 3 分钟；面试官中途追问时，可以在任意一页停下并打开右侧证据文件。

## 90 秒压缩版

这个项目基于 TencentGR-1M，并参考公开 OnePiece 方法、固定上游提交。我先把训练、候选编码和最后点击评测整理成可审计闭环：验证 Query 只使用目标之前的历史，最终在 78,921 个用户和官方 66 万候选上做分块精确 Top-10。

模型侧先做同预算 4×128 HSTU/Transformer 对照，HSTU 固定 seed 综合分提高 4.10%；再把 HSTU 扩到 8×512，综合分提高 25.63%。这两个实验分别回答架构和整体容量问题。

最有价值的是 SID 负结果。第一轮 SID 让综合分下降 5.87%，我定位到 225 万 pair 碰撞和辅助损失过强。零碰撞映射、首个 Epoch warm-up 和 0.02/0.05 权重消融把明显退化修复到与无 SID 持平。所有预测都做用户、Target、历史长度逐行对齐，产物通过 SHA-256 回读；所以我能说明每个数字的来源，也能明确单 seed 和评测协议的边界。

## 3 分钟逐页讲稿

### 第 1 页，0:00–0:55：问题与系统闭环

“这个项目的起点是 2025 腾讯广告算法大赛的 TencentGR-1M Baseline。数据规模是 100 万用户、478 万 Item 索引，官方评测候选约 66 万。原始代码给出了模型入口，但路径、设备和评测过程耦合较强，候选与 Item ID 还可能静默错位。

我的第一步是先冻结证据口径：使用固定 seed 做用户划分，对验证用户保留最后一次点击，Query 只使用 Target 之前的历史；排除没有点击或 Target 不在候选池的用户后，得到 78,921 行固定评测人口。候选编码和 Query 编码之后用分块精确内积取 Top-10，避免 ANN 误差混入消融。代码、配置、预测、指标和哈希一起交付。”

转场句：“有了固定协议，第二页的模型对照才有解释力。”

### 第 2 页，0:55–1:50：架构与容量证据

“模型侧我没有直接堆功能，而是先回答两个可区分的问题。第一个问题是编码器差异：保持 4×128、特征、Batch、Epoch、优化器、seed 和评测人口不变，只切换 HSTU 与因果 Transformer。HSTU 综合分 0.06634，Transformer 0.06373，点估计提高 4.10%。

第二个问题是当前资源范围内的容量扩展。HSTU 从 4×128 到 8×256，再到 8×512，综合分依次为 0.06634、0.07608 和 0.08335；8×512 相对 4×128 提高 25.63%。这里同时增加了深度和宽度，所以我只把它解释为整体 capacity scaling，不拆成单独的深度或宽度贡献。两组结论仍只有一个训练 seed，图上的区间只描述固定评测人口。”

转场句：“扩容给出了更强控制组，第三页用它检验 SID 是否真的带来收益。”

### 第 3 页，1:50–3:00：SID 负结果与修复

“第一轮在 8×512 HSTU 上加入两级 SID 辅助目标后，综合分从 0.08335 降到 0.07846，下降 5.87%。我没有把它写成 SID 无效，而是检查训练曲线和映射，发现 478 万 Item 中有 225 万发生 pair 碰撞，两个 SID 交叉熵还以等权方式直接加入主目标。

修复时，我先用容量平衡重分配把 pair 碰撞降到 0，再给辅助损失增加首个 Epoch 线性 warm-up，并比较 0.02 和 0.05 两档权重。0.02 的综合分恢复到 0.08346，与无 SID 的差值只有 +0.14%，配对区间跨 0，所以最终结论是修复到持平。0.05 的 Beam 生成召回更好，但全候选排序略低，说明两个目标之间存在权衡。

为了避免把评测处理误写成模型提升，我还用四个既有 checkpoint 补齐候选过滤和历史过滤的对齐重评。同一控制 checkpoint 变化 +2.61%，这是协议效应；掩码和 SID 的模型对照区间都跨 0。这个项目最能代表我的部分，是把实验问题、工程故障和结论边界连成一条可复查的证据链。”

收尾句：“如果您希望继续深挖，我可以从 HSTU 结构、InfoNCE 的 LogQ 校正、SID 生成，或者精确 Top-10 的显存设计中任选一个展开。”

## 10 分钟扩展版

### 0:00–1:00：项目边界

- 基于公开 TencentGR-1M、腾讯官方 Baseline，并参考固定提交的公开 OnePiece 上游代码。
- 目标是本地可复现、可审计的生成式推荐实验，不是官方参赛提交。
- 公开仓库保存代码、测试、配置和聚合指标；大权重与受限衍生产物按许可分层保存。

### 1:00–2:30：数据与评测人口

- 原始用户 1,001,845，Item 索引 4,783,154，官方候选约 660,000。
- 固定 seed 2025 的 90/10 用户划分产生 100,184 名验证用户。
- 留出最后一次 `action_type=1`，历史严格截止在 Target 之前。
- 1,745 人没有有效点击，19,518 人的 Target 不在候选池，最终保留 78,921 人。
- 用户、Target 和历史长度数组逐行冻结；所有变体必须通过相等性检查。

### 2:30–4:00：基础链路与 OnePiece

- 基础链路是 SASRec 风格因果 Transformer，含 ID、稀疏、数组和可选多模态特征。
- OnePiece 路线使用 HSTU 序列块、归一化 Query/Item 表征、温度缩放 InfoNCE 与 `-log q(item)` 采样偏差校正。
- HSTU 用 U/Q/K/V 联合投影、SiLU 权重、相对位置偏置和 U 门控；匹配的 Transformer 使用因果多头注意力与 FFN。
- 架构对照只切换编码器；系统级 Baseline 对比还改变损失、容量和参数化，不能混为一类证据。

### 4:00–5:30：精确检索

- 66 万候选向量常驻设备，Query 分批计算分数并立即保留 Top-10。
- HSTU 评测使用 128 个 Query 一批、660k 候选；基础 32 维模型使用 2,048 个 Query 一批。
- 这样不会物化完整的 `78,921 × 660,000` 矩阵；精确结果作为 ANN 的正确性基线。

### 5:30–7:00：架构与容量结果

- 4×128 HSTU 0.06634，匹配 Transformer 0.06373，固定 seed 提高 4.10%。
- HSTU 8×256 为 0.07608，8×512 为 0.08335；后者相对 4×128 提高 25.63%。
- 历史切片表明不同人群的收益不完全一致；总体数字不应被解释为每个分桶都相同。
- 每个配置只训练一次，多 seed 是稳定性验证的首要后续工作。

### 7:00–8:30：SID 诊断

- 第一轮存在 2,250,041 个碰撞 Item，辅助目标等权加入，综合分下降 5.87%。
- 容量平衡、top-k occupancy 重分配和 fallback 产生 4,783,154 个唯一 pair。
- 首个 Epoch warm-up 与 0.02 权重把明显退化修复到持平；0.05 改善 Beam 覆盖，但略损全候选排序。
- 当前零碰撞 SID 是全局 residual 近似，部分 Item 跨 L1 移动，不能声称严格复现上游层级 SID。

### 8:30–9:30：工程与故障恢复

- 移除硬编码路径和设备，增加 CPU/CUDA/Ascend 路由、smoke test 与断点恢复。
- 分片下载失败时保留已通过哈希的 11 片，只补传缺失部分，重组后验证整文件 SHA-256。
- 训练状态和同步状态分离，避免 watcher 假活导致重复训练。
- 公开回归测试当前为 149 passed、2 skipped；跳过项依赖特定运行环境，不代表正式训练已在本机重跑。

### 9:30–10:00：结论和下一步

- 当前最稳的架构证据来自 HSTU/Transformer 单变量对照。
- SID 的贡献是把失败诊断与修复闭环做实，当前不声称稳定增益。
- 下一步先跑多 seed，再比较严格层级 SID、生成解码覆盖和 ANN 召回/延迟权衡。

## 常见打断式追问

### “一句话说清你个人做了什么？”

我负责把上游方案变成可运行、可比较、可发布的实验系统：冻结数据与评测协议，完成 HSTU/Transformer 和容量/SID 对照，定位并修复 SID 退化，同时建立断点、逐行对齐、哈希和分层发布门槛。

### “项目里最难的问题是什么？”

最难的是让分数具有可解释性。候选 ID、历史截断或评测过滤只要有一处漂移，模型仍然会运行，但对照结论会失效。因此我把协议哈希、逐行人口对齐和同 checkpoint 重评放在模型优化之前。

### “为什么这个项目值得写进简历？”

它同时提供了架构单变量证据、规模实验和真实失败修复。每个结果都有配置、预测、指标和哈希入口，面试中既能谈算法，也能谈系统、统计边界和工程治理。
